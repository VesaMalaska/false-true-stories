# Lightweight Runtime and Run Profiles — Validation Review

## Purpose

Scenario-based review criteria for the lightweight runtime architecture and explicit Story Run Profiles. These walkthroughs validate framework behavior, not absolute provider latency.

## Scenarios

1. **Zero configuration:** defaults apply; no optional profile question blocks launch; effective profile is balanced/cinematic/rich.
2. **Story-mode listener:** narrator carries ordinary motion; major decisions may still yield; user can seize control anytime.
3. **Player-mode listener:** more frequent meaningful open hand-offs; no compulsory menu behavior.
4. **One-turn steering-wheel grab:** explicit protagonist action is followed immediately; baseline profile is unchanged.
5. **Temporary listen mode:** narrator initiative rises for the requested scope; stored baseline remains.
6. **Persistent profile change:** “from now on” updates the baseline, persists at an appropriate checkpoint, and affects no other run.
7. **Incremental continuity:** concise deltas accumulate; state/history are consolidated at checkpoint rather than rebuilt after every response.
8. **Dormant world fact:** consult authority, refresh active context, and return to lightweight mode rather than inventing replacement truth.
9. **Session recovery:** reconstruct packet from authority; no canon depends on the lost temporary packet.
10. **Non-technical user:** framework machinery works without asking the user to understand technical records, profile keys, packets, or checkpoints.
11. **Open hand-off:** default prompt is open; menus are optional; plausible custom actions remain valid.
12. **Lightweight continuation:** “continue” does not reopen setup or reinterpret every framework document without cause.

## Acceptance criteria

Defaults are normative and non-blocking; interaction/pacing/detail are independent; protagonist override is always available; persistent/temporary/one-turn semantics are explicit; Runtime Packet is derived/disposable; deltas/checkpoints preserve continuity; escalation is explicit; setup/live responsibilities are distinct; launchers activate the model; README remains approachable.

## Live validation

Follow specification review with real story use. The Maximilian Toranaga example is suitable because the earlier run exposed the motivating findings: enjoyable momentum, useful relatively low forced-decision frequency, moments where the listener wanted direct control, and noticeable delay between continuation requests and narration.

Evaluate narrative quality and perceived responsiveness separately.
